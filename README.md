# GPUStatus

多机 GPU / CPU / 内存监控看板。**中心主动采集**、**目标机器零安装**、**轻量 SQLite 留存用量记录**。

- 纯 SSH 轮询采集,客户 GPU 机器上**不需要装任何东西**(不装 agent、不装 Python、不开端口)
- 后端依赖极少(`better-sqlite3` + `jsonc-parser`),HTTP 服务用 Node 内置 `node:http`
- **目标机器零依赖**才是硬约束:只经 SSH 调用目标机上的 `sh` / `awk` / `nvidia-smi`,不装任何东西
- 按用户名展示:哪台机器、哪张卡、占多少显存、GPU 利用率多少
- 机器采集失败时状态灯 **绿 → 黄 → 红**,并在事件表留下记录
- 每小时的用户用量汇总**永久保留**,原始采样可定期清理,便于年终统计
- 要统计哪些机器,只改一个配置文件

## 1. 架构

```
                   ┌──────────────────────── GPUStatus 部署机 ───────────────────────┐
                   │                                                                 │
  config/hosts.json│   Collector ──ssh(复用连接)──┐                                  │
   (要监控哪些机器) │      │                       │                                  │
                   │      │ 每次采集 = 1 条 ssh 命令 │                                  │
                   │      ▼                       │                                  │
                   │   State(内存最新状态)          │                                  │
                   │      │  ├── 状态灯状态机 绿/黄/红 │                                │
                   │      │  └── 变更 → events 表    │                                │
                   │      ▼                       │                                  │
                   │   SQLite (better-sqlite3)    │                                  │
                   │    ├── 原始采样(默认留 7 天)     │                                │
                   │    └── usage_rollup(永久)      │                                │
                   │      │                       │                                  │
                   │      ▼                       │                                  │
                   │   HTTP API + SSE ────────► React 前端 (web/dist)                  │
                   └─────────────────────────────────────────────────────────────────┘
                                    │
                    ssh 只读执行远程探针(不落盘、不联网)
                                    ▼
        ┌───────────────┐  ┌───────────────┐  ┌───────────────┐
        │   gpu19       │  │   gpu20       │  │  (更多机器…)   │
        │ 8×RTX 5880Ada │  │ 8×RTX 6000D   │  │               │
        │ 无需安装任何组件 │  │ 无需安装任何组件 │  │               │
        └───────────────┘  └───────────────┘  └───────────────┘
```

**数据流方向**:中心 → 目标机器(拉取)。目标机器完全被动,不向中心推送任何数据,
因此新增客户机器不需要在客户侧做任何配置。

### 采集原理

每次采集对每台机器执行 **1 条 SSH 命令**(`ssh <host> sh -s < remote-probe.sh`),
远程探针是一个 POSIX sh 脚本,只用系统自带命令:

| 数据 | 来源 |
|---|---|
| 每张卡的利用率 / 显存 / 温度 / 功耗 / 风扇 | `nvidia-smi --query-gpu=... --format=csv,noheader,nounits` |
| 每个进程占用的显存(MiB) | `nvidia-smi --query-compute-apps=gpu_uuid,pid,process_name,used_memory` |
| **每个进程的 SM 利用率** | `nvidia-smi pmon -c 1` |
| 进程属主用户名 | `ps -o pid=,user= -p <所有客户端pid>`(一次调用解析全部) |
| CPU / 内存 / 负载 / 磁盘 | `/proc/stat`、`/proc/meminfo`、`/proc/loadavg`、`df` |

CPU 使用率不在目标机器上 `sleep` 采样,而是把 `/proc/stat` 的原始 jiffy 计数带回中心,
由后端用**相邻两次采集的差值**计算 —— 既不增加延迟,又得到整个采集周期内的真实均值。

### 为什么探针要特意写成"单次 awk 解析"

初版探针每个字段都用一次 `$( ... )` + `sed`/`tr` 格式化,结果是 **~200 次 fork**,
单次采集耗时 1.67s(其中 1.16s 是 system 时间)。由于这是每台机器、每一轮都要付的成本,
现已改为:**原始命令输出按 section 流式送入单个 awk 程序**,由 awk 统一解析 + JSON 转义。
fork 数降到 ~12 次,采集耗时降到 **0.7~1.0s**,且几乎全部是 `nvidia-smi` 自身的耗时。

## 2. 环境要求

### 部署机(跑本服务的机器)

- **Node.js ≥ 20**(推荐 22/24 LTS;数据库用 `better-sqlite3`,从预编译包安装,不需要编译器)
- 能免密 SSH 登录所有被监控机器(密钥认证)
- 前端构建需要 npm(仅首次构建)

### 被监控机器(客户 GPU 机器)

**不需要安装任何东西。** 只需要:

1. 部署机能用密钥 SSH 登录(把部署机的公钥加到目标机 `~/.ssh/authorized_keys`)
2. 系统里有 `sh`、`awk`、`sed`、`grep`、`ps`、`df`、`hostname`、`uname`、`date`(Linux 默认都有)
3. 有 `nvidia-smi`(GPU 机器本来就有)

> 探针是**只读**的:不写任何文件、不访问网络、不需要 root。
> 即使 `nvidia-smi` 挂了,探针仍会返回合法 JSON 并把错误上报到看板,而不是让整台机器失联。

### 配置免密登录

```bash
# 在部署机上生成密钥(如果还没有)
ssh-keygen -t ed25519 -N '' -f ~/.ssh/id_ed25519

# 分发到各 GPU 机器
ssh-copy-id gpu19
ssh-copy-id gpu20

# 验证:应当无需输入密码即可执行
ssh gpu19 'nvidia-smi --query-gpu=index --format=csv,noheader'
```

## 3. 快速开始

```bash
# 1. 安装前端依赖并构建(只需在部署机执行)
npm --prefix web install
npm run build

# 2. 从模板生成自己的配置,再编辑要监控的机器列表
cp config/hosts.example.json config/hosts.json
vi config/hosts.json

# 3. 先单次试跑,确认能采到数据(不启动服务)
node server/index.js --once

# 4. 启动
npm start
# 打开 http://<部署机IP>:8787
```

> **为什么配置要自己复制一份**:`config/hosts.json` 里是你的真实机器名和管理密码哈希,
> 所以它**不进版本库**(见 `.gitignore`)。仓库里只有脱敏的 `config/hosts.example.json`。
> 如果忘了复制,服务也能起来 —— 会用示例配置并打印醒目提示,只是那两台 `gpu01/gpu02` 连不上。

`--once` 的输出会直接打印每台机器的 CPU/内存/各卡利用率,以及每个用户占了几张卡、多少显存:

```
[2026-09-15 11:38:10] gpu19    ok      cpu=7.5% mem=7.8% gpus=8 [0:100% 1:100% ...]
[2026-09-15 11:38:10]     alice: 8 GPU(s) [0,1,2,3,4,5,6,7] 375120 MiB sm~98.8%
```

> `--once` 模式下 **CPU 会显示 `-`**,这是正常的:CPU 使用率由相邻两次采集的
> `/proc/stat` 差值算出,单次运行没有"上一次"可比。服务常驻运行时第一轮之后就会正常显示。

### 开发模式(前后端分离)

```bash
node server/index.js --no-poll   # 只跑后端 API,不采集
npm --prefix web run dev         # Vite 开发服务器,自动代理 /api 到 8787
```

## 4. 配置说明(`config/hosts.json`)

支持注释(JSONC)和尾逗号,因为这是给人编辑的文件。

```jsonc
{
  "server": {
    "port": 8787,
    "bind": "0.0.0.0",
    "web_dist": "web/dist"      // 前端构建产物目录,也可交给 nginx 托管
  },
  "poll": {
    "interval_ms": 15000,       // 采集间隔
    "timeout_ms": 12000,        // 单次采集超时
    "stale_after_ms": 45000,    // 超过这么久没有成功采集 → 黄灯
    "down_after_failures": 3    // 连续失败这么多次 → 红灯
  },
  "ssh": {
    "user": "",                 // 非空则拼成 user@host
    "control_persist_s": 60,    // SSH 连接复用,首轮握手后续复用,15s 间隔几乎零开销
    "connect_timeout_s": 6,
    "extra_options": []         // 例如 ["-i", "/home/gpustatus/.ssh/id_ed25519"]
  },
  "db": {
    "path": "data/gpustatus.db",
    "raw_retention_hours": 168  // 原始采样保留 7 天;0 = 永久保留
  },
  // 显示名:默认从机器自己上报的 hostname 解析,不需要逐台命名
  "naming": {
    "strip_domain": true,       // server19.example.com → server19
    "capitalize": true          // server19 → Server19
  },
  "hosts": [
    {
      "id": "gpu19",            // 唯一标识,用于 URL 和数据库主键(改名会丢失该机历史)
      "ssh": "gpu19",           // ssh 目标:只是"怎么连上去",不是显示名
      "group": "NPUCVR",        // 分组标签,便于筛选
      "expect_gpus": 8          // 预期卡数;不符会在界面报警(掉卡/驱动异常)
      // 可选 "label": "自定义名字" —— 设了就优先用它,不再从 hostname 解析
    }
  ]
}
```

### 实验室 / 站点名称

顶栏那个名字是**整个部署**的名字,不是每台机器的属性:

```jsonc
"site": "NPUCVR"     // 留空则显示 GPUStatus
```

它只在页面顶部出现一次,以及浏览器标题里。**不要**再给每台机器写 `"group": "NPUCVR"` ——
那会让同一个名字在 6 张卡片上重复 6 次。实测已确认:机器列表的渲染结果里不再包含这个名字,
有测试盯着。

`group` 字段仍然保留,但**只在它和 `site` 不同时才显示**,用于真正的机器分组
(比如不同机房、不同代次的卡):

```jsonc
{ "id": "gpu14", "ssh": "gpu14", "group": "A100机房" }   // 会显示标签
{ "id": "gpu19", "ssh": "gpu19" }                        // 不显示
```

---

### 机器显示名从 hostname 自动解析
配置里的 `ssh` 只是**怎么连上去**(往往是本地 ssh 别名,如 `gpu19`),
而界面显示的名字来自**机器自己上报的 hostname**,因此新增机器不用起名:

| hostname | 显示名 |
|---|---|
| `server19.example.com` | `Server19` |
| `server20.example.com` | `Server20` |
| `gpu-node-01.example.com` | `Gpu-Node-01` |
| `A100-node2` | `A100-Node2` |
| `192.0.2.1` | `192.0.2.1`(IP 不切域名、不改写) |

优先级:**配置里的 `label` > hostname 解析 > 配置 `id`**。
最后一个兜底用于"服务刚启动、还没成功采集过任何一次"的瞬间。

解析规则只在名字部分改首字母(以及 `-`/`_` 分段后的首字母),**域名部分不动**,
也不会把 `A100` 这类已有大写改坏。

> `id` 是数据库主键,**改 `id` 等于换了一台机器**,该机历史会断开。
> 想让界面换个叫法,改 `label`,或者干脆什么都不改 —— 让它跟着 hostname 走。

> `expect_gpus` 是有用的运维信号:某张卡从总线上掉了或者驱动异常时,卡数会变化,
> 界面会直接标出 `显卡 7/8`。

## 5. 磁盘目录按机器配置

每台机器真正需要盯的目录不一样(`/home`、`/data1`、某个 scratch 目录……),
所以**每台机器可以单独配置目录列表**:

```jsonc
{
  "id": "gpu19",
  "ssh": "gpu19",
  "expect_gpus": 8,
  "disks": ["/", "/home", "/data1"]   // 留空 = 自动列出所有挂载点
}
```

配置的路径用 `df` 检查,**填目录即可,会自动解析到它所在的文件系统**。因此:

- `/` 和 `/tmp` 在同一个卷上时,两个数字会一样 —— 界面上会显示 `路径 → 挂载点` 让你看清
- 目录不存在会明确标注「**目录不存在**」,而不是悄悄不显示(那会被误以为配置没生效)
- 留空则该机自动发现挂载点(界面标注「自动发现」,提醒你去配置)

`disks_configured` 由服务端明确给出,不靠前端猜 —— 因为"配置的目录恰好就是挂载点"和
"自动发现的挂载点"在数据上完全一样,区分不了。

> 实测这套机制是有用的:`/home` 在 Server19 上是 **100%**(3.3TB 只剩 9.9GB),
> 而自动发现模式下列出的 8 个挂载点里它并不显眼。

---

磁盘每个文件系统一个**独立的方块**(浅底 + 细边框),不是一个挨一个地排成一行 ——
裸排的时候路径、进度条、数字连成一片,分不清哪个到哪个。

### 网络挂载(NFS)单独处理

`/share`、`/remote_userdata` 这类 NFS 目录**不统计容量**,只检查是否健康挂载。原因实测很直接:

```
Server14 /share: 99%  87TiB        Server17 /share: 99%  87TiB
Server16 /share: 99%  87TiB        Server19 /share: 99%  87TiB
```

**六台机器报的是同一组数字** —— 因为容量属于文件服务器,不属于本机。六行一模一样的
"99% / 87TiB" 把真正有差异的本地数据盘全淹了。

配置在每台机器的 `net_mounts`,界面显示为一行状态:

```jsonc
{ "id": "gpu19", "ssh": "gpu19", "net_mounts": ["/share", "/remote_userdata"] }
```

显示在**每台机器自己的卡片里**,紧跟磁盘区,但**形态和磁盘刻意不同** ——
它是一条**横贯整行的状态带**,标签和所有挂载在同一行:

```
网络挂载   ● remote_userdata 未挂载   ● share 已挂载              1 项异常
```

理由是这个区域的情况是**固定**的:每台机器挂的都是站点级的那两三个 NFS 目录,
而且只关心"在不在"。所以不需要磁盘那种变长列表的网格。

前两版都失败过,原因值得记下来:

- **照抄磁盘样式**(等宽方块网格)→ 不对:磁盘是每台机器各不相同、数量可变的数据卷,
  网格是合适的;网络挂载是固定短列表
- **标题独占一行、挂载排在下面** → 两个挂载只占卡片一半宽度,另一半空着,看着像坏了

整行状态带没有空的一半,只占一行高度,而且和页面上任何东西都不重样。

- 机器从未采集过 → 该机不显示这一行(状态未知,不臆断)
- 该机器没有这个挂载 → 不显示该项,而不是显示成异常

| 状态 | 含义 |
|---|---|
| 正常(绿) | 已挂载且可读写 |
| 只读(黄) | 已挂载但是 `ro` —— 是状态,不一定是故障 |
| 异常(红) | **没有真正挂载上**,或者挂上了但没响应 |

判定标准就一条:**有没有真的挂上**。

一开始我把 `autofs`(只有自动挂载器条目、尚未触发)当成"不算故障",理由是首次访问时会
自动挂上。**这个判断是错的**,已改:挂载写在 `net_mounts` 里就意味着它**应该**挂着,
自动挂载器将来会不会挂上,对正在对比两台机器的人没有意义 —— 一台有、一台没有,那就是异常。

探针仍然区分 `autofs` / `missing` / `stale` 三种情况(诊断信息有用),只是**颜色不再由原因决定**,
三种都显示「异常」,具体原因在鼠标悬停提示里。

> 实例:Server18 的 `/remote_userdata` 只有 `autofs` 条目、没有 `nfs4` 挂载,
> 而另外 5 台机器都正常挂着 —— 这就是需要被发现的情况。

> 「按需挂载」这个状态是实测逼出来的:Server18 的 `/remote_userdata` 在 `/proc/mounts`
> 里只有 `autofs` 行、没有 `nfs4` 行。如果直接报「未挂载」就是误报 —— 它只是还没被访问过。

配置了 `net_mounts` 才有意义:**没配的话,一个消失的挂载会静默消失**;配了之后缺失会显示成
「未挂载」。

**顺带修掉一个隐患**:之前自动发现用的是不带参数的 `df -P -k`,它会枚举所有文件系统 ——
**NFS 服务器一旦挂死,`df` 会一直阻塞,整个探针就卡住了**。现在先读 `/proc/mounts` 筛出本地
文件系统,再对这份明确清单调用 `df`,永远不会碰到网络。

### GPU 名字用短名

nvidia-smi 报的名字又长又不统一(`NVIDIA GeForce RTX 4090` vs
`NVIDIA RTX 5880 Ada Generation`),塞不进表格列。用一个映射表换成短名:

```jsonc
"gpu_names": {
  "NVIDIA GeForce RTX 3090": "RTX 3090 (24G)",
  "NVIDIA GeForce RTX 4090": "RTX 4090 (24G)",
  "NVIDIA L40": "L40 (48G)",
  "NVIDIA RTX 5880 Ada Generation": "RTX 5880 Ada (48G)",
  "NVIDIA RTX 6000D": "RTX Pro 6000D (84G)"
}
```

**键必须是 nvidia-smi 报的原始字符串**(用 `nvidia-smi --query-gpu=name --format=csv,noheader`
可以查到)。没映射到的卡会自动回退成去掉厂商前缀和营销后缀的短名,例如
`NVIDIA RTX 5880 Ada Generation` → `RTX 5880 Ada`,所以漏配也不会显示成一长串。

解析在**服务端**做,接口里同时给出原始名 `name` 和显示名 `display_name`,
界面只渲染 `display_name` —— 这样界面、接口、以后导出的报表用的是同一个名字。

显示位置:**表格里独立一列**,序号单独一列:

```
 #   型号                 利用率   显存
 #0  RTX 3090 (24G)       100%    16.9 GiB / 24 GiB
 #1  RTX 3090 (24G)       100%    17.0 GiB / 24 GiB
```

型号用正常字号和正文色,不是灰色小字 —— 它和利用率、显存一样是你要读的数据,
不该被降级成脚注。

**点整行任意位置都能展开**该卡的进程明细,不用去点最前面那个小图标(图标保留 ——
它是"这行可以展开"的唯一提示)。可展开的行光标是手型。「用户」页的表格同样如此。

> 管理页的机器表格**故意没有**开启点行展开:那一行的单元格里是输入框,
> 点一下应该是去编辑那个字段,不该被当成展开整行。

### 有展开行的表格不能同时用 `scroll={{x:'max-content'}}`

这是一个踩过的坑,记在这里免得再犯:带展开行的 `Table` 如果同时设了
`scroll={{x:'max-content'}}`,**一旦展开某行,其余所有列会塌成 0 宽度,表头直接消失**。

原因是 `max-content` 让 antd 按行内容推算列宽,而展开行是**一个横跨所有列的单元格**,
它把这套推算带偏了。

判断方法很简单:**要么用 `max-content`,要么用展开行,不要两个一起用**。
本项目所有表格都已核对过没有这个组合。

也不做"同型号只在标题写一次"那类优化:那需要判断统一/混插两种分支,
混插时还得特殊处理。逐行显示没有分支,混插机器也自然正确。

### 磁盘:全局排除列表

```jsonc
"disk_exclude": ["/", "/boot/efi"]     // 默认值
```

`/` 是系统盘、`/boot/efi` 是几百 MB 的固件分区,都反映不了"任务能不能写数据",却挤占了
真正要看的列表。**在探针里就过滤掉**,所以既不采集、不入库,也不会出现在管理页的勾选列表里。

做成可配置而不是写死:万一哪天系统盘写满导致故障,改配置就能加回来,不用改代码。

另外探针还有三条自动过滤规则(实测逼出来的):

- **只读挂载不统计** —— 写不进去的文件系统,剩余空间没有意义。这条干掉了
  `/var/snap/firefox/common/host-hunspell`(snap 建的只读 bind mount,出现在三台机器上)
- **同一设备只报一次** —— 同一个文件系统常被挂到多个位置,每个都报一遍就是重复数字
- 内核/伪文件系统、snap 镜像

## 7. 管理页面 `/admin`

网页里「管理」页签,可以:

- 增删机器,改 `id` / SSH 目标 / 显示名 / 分组 / 预期卡数
- **给每台机器配磁盘目录**(输入路径回车即可)
- 改采集间隔、超时、黄灯/红灯阈值、显示名规则

保存后**立即生效,无需重启**:服务会在内存里换掉配置,已建立的 SSE 连接和采集计划都不受影响。
保存前会先写到临时文件并用正常加载器校验一遍,所以**不会把一个会让服务启动失败的配置写进去**;
第一次保存前还会自动留一份 `config/hosts.json.bak`(因为保存会按标准注释重新生成文件,
你手写的注释会被替换)。

### 设置密码

管理页面默认**不可用**。在 `config/hosts.json` 里二选一设置,然后重启:

```jsonc
"admin": {
  // 推荐:配置文件里不出现明文密码
  "password_sha256": "把下面命令的输出粘进来",
  // 或者(不推荐)
  // "password": "明文密码",
  "session_hours": 12
}
```

```bash
node -e "console.log(require('crypto').createHash('sha256').update('你的密码').digest('hex'))"
```

几个刻意的设计:

- **两个都不写 = 管理页面不可用**,不会写入 `change-me` 之类的默认密码。
  这一条有测试盯着 —— 一个公开已知的默认密码等于没有密码。
- **密码不能在管理页面里改**,只能改文件重启。这样密码丢了永远能救回来,
  不需要依赖那个被密码保护的界面。
- 会话是 `HttpOnly` + `SameSite=Strict` 的签名 Cookie,带有效期;改过期时间会让签名失效。
- 同一来源连续失败 5 次锁定 15 分钟。
- **服务是 HTTP,密码在网络上是明文的。** 可信内网之外请套 HTTPS 或走 SSH 隧道。

## 8. 界面与主题

### 布局:表格式,一卡一行

每台机器是一段:**一行机器摘要 + 一张 GPU 表**。

```
● Server19  server19.example.com   NPUCVR      CPU 7.2% 内存 34.7/440GiB 负载 29.4 卡 8/8 型号 8×RTX 5880 Ada 驱动 580.178.04
┌──────┬────────────┬──────────────┬─────────────────┬───────┬───────┬─────────┐
│ GPU  │ 用户        │ 利用率        │ 显存             │ 温度   │ 功耗   │ PID     │
├──────┼────────────┼──────────────┼─────────────────┼───────┼───────┼─────────┤
│ #0   │ alice │ ▓▓▓▓▓▓ 99%   │ ▓▓▓▓▓ 45.8 GiB  │ 86°C  │ 285W  │ 2786330 │
│ #1   │ alice │ ▓▓▓▓▓▓ 99%   │ ▓▓▓▓▓ 45.8 GiB  │ 88°C  │ 271W  │ 2786331 │
└──────┴────────────┴──────────────┴─────────────────┴───────┴───────┴─────────┘
```

**一行 = 一个进程**(空闲的卡也占一行,标"空闲")。这样:

- 数字按列对齐,可以竖着扫一列比较,而不是在 16 个方块里找
- 多人共享一张卡时,每人一行,各自的 SM 利用率和显存互不混淆
- 机器多了也不会失控(20 台机器 = 20 段表,而不是 160 个卡片)

利用率取的是**该进程的 SM 利用率**(来自 `pmon`)—— 这才是"这个用户用了多少 GPU"。
空闲行显示的是整卡利用率。显存也按进程归属,空闲行显示整卡占用。

型号相同的时候在机器摘要里写一次(`8 × RTX 5880 Ada`),不在每行重复。

界面只放数据,不放"这个系统是怎么工作的"这类介绍 —— 它们是给人**读一次**的,
却会长期占据视觉位置。判断规则很简单:**会随机器状态变化的信息留下,不变的说明移走**。

- 页脚整条(`数据经 SSH 只读采集,目标机器无需安装任何组件`)—— 连同同一行的

- 主题状态在页脚的重复显示(顶部开关已经表明了)

保留下来的两处,是因为它们确实是**数据**而不是说明:

### 显卡健康:降频检测

只看利用率会漏掉一类问题:**卡在 100% 利用率、温度也不算离谱,但实际只跑出三成速度。**

`nvidia-smi` 的 `clocks_throttle_reasons.active` 是一个位掩码,我们直接解出来:

| 位 | 含义 | 是否算问题 |
|---|---|---|
| `0x001` | 空闲(GpuIdle) | **否** —— 空闲卡本来就降频 |
| `0x002` | 应用时钟限制 | 否 |
| `0x004` | 功耗墙 | 是(但满载撞功耗墙是正常配置) |
| `0x008` `0x040` `0x080` | 硬件降频 / 热降频 | 是 |
| `0x010` `0x100` | 同步加速 / 显示时钟 | 否 |
| `0x020` | **热降频** | 是 |

- 单个卡:型号旁出现 `⚠ 降频` 标签,悬停显示原因、`SM 时钟/最高时钟`、功耗上限
- 整机:标题下出现告警行,例如 `5/8 张卡热降频`
- **空闲的卡不报警** —— 判据是"有降频位 **且** 卡不空闲",否则每台没人用的机器都会告警
- 掩码读不到时存 `NULL` 而不是 `0`:"读不到"和"没降频"是两回事

采集这 5 个字段(降频掩码、SM 时钟、最高时钟、功耗上限、pstate)**不增加任何进程** ——
它们搭在原有那次 `--query-gpu` 上,实测 0.11s → 0.12s。

> 实际发现的例子:Server19 有 5 张卡处于热降频,SM 时钟 930 MHz / 最高 3105 MHz,
> 风扇已 100% 仍压不住,累计热降频时长达 46 小时 —— 而只看看板上的利用率,它是满绿的。

### 界面上用序号,数据里存稳定标识

表格首列显示 **GPU 序号**,因为那是人们认得的数字 —— `ssh` 进去 `nvidia-smi` 打印的就是它,
`nvidia-smi -i N` 用的也是它。

**但序号是会变的**:所有机器物理上都是 8 卡,跑不了程序的卡会在开机后被屏蔽掉,
`nvidia-smi` 会把剩下的重新编号 —— 今天的 `#3` 和下周的 `#3` 可能是两张不同的物理卡。

所以稳定性放在**数据**里而不是界面上:每次采样都同时记录 **PCIe 槽位**
(`gpu_sample.bus_id`,如 `37:00.0`)和 UUID。屏蔽不会移动槽位,凡是需要跨时间识别的
分析都该用槽位而不是序号 —— **界面完全不需要显示它,这件事照样成立**。

(曾经把首列改成槽位,已按"用户不需要理解这些"改回序号。)

**统计本来就不受影响**(实测核对过):`usage_rollup` 主键是 (小时, 机器, 用户名),
不含任何显卡标识;`gpu_sample` / `proc_sample` 同时存了序号、UUID 和槽位;所有 SQL 里
**没有任何查询按序号分组或过滤**。

### 卡数告警跟机器自己的近期基线比

固定 `expect_gpus` 在这个环境里是错的:它会在**开机 8 卡 → 屏蔽成 6 卡**这个
**预期行为**上报警,而且你一调整屏蔽范围它就过期了。

现在改成跟**这台机器自己最近两小时的最高值**比:低于它就报
`显卡数量从 6 降到 5`。故意屏蔽造成的下降会在高位数值移出窗口后自动停止上报。

> **这个取舍要说清楚**:两小时后,一张真的坏掉的卡就不再报警了 —— 它留在**事件日志**里。
> 永远不消失的红色角标正是人们学会忽略的东西。
>
> `expect_gpus` 仍然有效:配置了就按配置来(那是你明确表达意图),没配就走基线。

另外**任何**卡数变化都会记一条事件(`显卡数量 8 -> 6`),因为"这台以前是 8 张、
现在 6 张"正是运维要问的问题,它属于日志而不属于角标。

### 用户名必须完整

`ps` 在**多列输出**时会用默认列宽而不是按内容自适应,其中 `USER` 默认 8 字符。
所以 `ps -o pid=,user=,etime=` 会把 `luzhicheng` 读成 `luzhich+`。

> 单列 `ps -o user=` 恰好会自适应,所以这个 bug 是在加 `etime` 那一列之后才出现的。

**这不是显示问题,是账目问题**:截断后的短名进了 `usage_rollup`,于是一个人的
GPU 时被拆成两行、挂在两个名字下(实测 `luzhich+` 1.9 GPU时 + `luzhicheng`
132.9 GPU时)。年终统计会算错。

- 探针改用 `ps -o pid=,user:32=,etime=`(32 是 Linux 用户名长度上限,不可能截断)
- 升级时**自动修复已有数据**:把截断名合并回全名。合并只在**恰好一个**更长的
  用户名以同一前缀开头时进行;两个人共享 7 字符前缀时无法从数据判断,那种情况
  保持原样并报告,不猜
- 合并是**累加**而不是改名:`usage_rollup` 的主键是 `(小时, 机器, 用户名)`,
  全名那一行通常已经存在,直接改名会撞主键或丢掉一边的 GPU 时
- 加了守护测试:`ps` 的格式串里 `user=` 必须带宽度

### 颜色只表示"出问题了"

告警色阶(绿→琥珀→红)**只留给坏掉或即将坏掉的读数**:

| 指标 | 用什么色 | 为什么 |
|---|---|---|
| 磁盘占用 | **告警色阶** | 盘满 → 任务写不了 checkpoint |
| 系统内存 | **告警色阶** | 内存耗尽 → OOM 杀进程 |
| 温度 | 达降频点转红 | 性能正在被悄悄丢掉 |
| **显卡利用率** | 中性(在用=蓝,空闲=灰) | 卡忙是目标,不是故障 |
| **显存占用** | 中性(同上) | 显存满 = 任务在用自己申请的量 |
| CPU | 中性 | 机器在干活 |

原因是这条原则一旦破例,颜色就不再有信息量:显存占用曾经走告警色阶,于是**每一台
正常忙碌的机器都画成一片红**,结果就是没人再看红色。

### 散热余量(哪台机器散热吃紧,一眼可见)

机器卡片上第四个指标:**所有卡里最高的一张温度,以及它距降频点还有多少度**。

```
gpu17   61°C   距降频 19°C
gpu20   66°C   距降频 14°C
gpu16   69°C   距降频 11°C
gpu18   74°C   距降频 6°C
gpu14   79°C   距降频 1°C     ← 也快到临界了
gpu19   87°C   3 张卡近期热降频  ← 已经在降频
```

- 进度条是**距降频点的距离**,不是某个随意最大值的百分比 —— 100% 就是"要开始降频了"
- 颜色**只依据事实**:有卡真的因热降频 → 红;温度达到降频点 → 琥珀;否则正常色。
  把摄氏度直接喂给 `severity()` 会把健康的 56°C 画成琥珀色
- **80°C 是实测得出**,不是文档里的规格:全机群 2.8 万个样本中,热降频位最早出现在
  80°C 并在此之上陡增。代码和 README 都注明了这一点,而不是假装它是规范值

卡级详情里的**功耗**也改成 `244 / 285 W  86%` 的形式 —— 单看"212W"没有意义,
`212/285` 是有余量,`212/220` 是卡在功耗墙上。

### 每台机器的展开详情

标题栏右侧的「详情」开关展开后有三块内容。

#### 1. 趋势图(一个图 + 两个选择器)

**左侧选指标,右侧选时间档位(24 小时 / 3 天 / 7 天 / 30 天)** —— 一个图而不是一排图。

原来的历史页同时画四张图,意味着其中三张永远挡在那里(实际只有利用率被看过)。
切换是一个主动动作,所以屏幕保持干净,而增加一个指标不占任何视觉空间。

可画的 8 个指标:

| 指标 | 说明 |
|---|---|
| 显卡利用率 | 整机所有卡平均 SM 利用率 |
| 显存占用 | 显存**容量**占用比例 |
| **显存带宽** | 显存**带宽**利用率 —— 与上一个不是一回事,见下 |
| CPU 利用率 | 该机器整体 CPU |
| 系统内存 | 系统内存占用比例 |
| 温度 | 所有卡里最高的一张 |
| 整机功耗 | 所有卡功耗之和 |
| **显卡降频占比** | 该小时内平均有多少比例的显卡时间处于热降频(**功耗墙不算**) |

显存带宽和显存占用放在一起才看得出问题出在哪:

```
算力 80% / 带宽 26%  →  算力受限,正常
算力 30% / 带宽 85%  →  卡在数据搬运,dataloader 该查了
```

> 前四个指标(`cpu_sum` / `sysmem_sum` / `memutil_sum` / `throttle_sum`)是后加的列。
> 升级时会**自动从明细表回填**,所以老数据也能切换查看,不会因为指标是新的就一片空白。
>
> 踩坑记录:回填 SQL 里判定降频的位掩码我手写成了 `236`,而那几个位加起来是 `232` ——
> 236 多包含了功耗墙位,于是"仅撞功耗墙"的 Server18 被算成 8 张卡降频。改用
> 命名位常量的或运算后修正。

#### 2. 机器信息与采集可靠性

| 字段 | 来源 | 为什么放在这里 |
|---|---|---|
| 主机名 / SSH 目标 | 探针 / 配置 | 核对是哪台 |
| 内核 / 显卡驱动 | `/proc` + `nvidia-smi` | 驱动兼容问题排查 |
| **PCIe 链路** | `pcie.link.*` | 见下 |
| 采集成功 / 总次数 / 失败次数 | 状态机 | 判断这台机器是不是一直不稳 |
| 上次采集耗时 | 计时 | 明显变慢说明 SSH 或机器本身有问题 |
| 时钟偏差 | 前后端时间戳 | 时间对不上会导致"多久没更新"算错 |
| 内存 / Swap / 负载 1·5·15 / IO 等待 / 进程数 | `/proc` | 排查 IO 瓶颈时用 |
| 显卡 UUID(可折叠) | `nvidia-smi` | **报修时要报的号** |

**PCIe 链路单独说**:卡如果协商到了比它支持的更窄的链路,会明显变慢,而**利用率、
温度、功耗全都正常** —— 页面上没有任何别的数字能看出来。繁忙的卡
`width < width_max` 就是故障(转接卡、插槽、接触不良),整机会出一条
`pcie_degraded` 告警。

> 判据用**宽度**不用代数:PCIe 链路在空闲时会把**代数**降下来,所以
> `gen < gen_max` 是常态,不能当故障;宽度不会这样。

#### 3. 卡级详情(展开某张卡的进程表时)

一行紧凑遥测:**SM 时钟 / 显存带宽 / 风扇 / P-State / 功耗上限 / PCIe / 降频原因**。

其中 **显存带宽利用率**(`utilization.memory` 对应的字段)从项目第一天就在采集、
也在入库,但**一直没有暴露到接口上**,直到这次才发现。它回答的是
"这个任务卡在算力上还是卡在数据搬运上":

```
算力 80% / 带宽 26%  →  算力受限,正常
算力 30% / 带宽 85%  →  卡在数据搬运,dataloader 该查了
```

进程表新增 **「已运行」** 列(`ps -o etime`,搭原有那次 `ps` 调用,不增加进程),
用来发现"忘记关的训练任务占着卡好几天"。

> 降频原因的着色区分严重程度:**热降频/硬件降频**是红色(散热问题,要处理),
> **功耗墙**是琥珀色 —— 满载时撞功耗墙是卡的正常表现,画成红色会让人学会忽略红色。

**「近 1 小时热降频」是必需的一列,不是补充。** 降频掩码是**瞬时值**,而接近
温度上限的卡会在两种原因之间来回跳:Server19 同一张卡这一秒报"功耗墙"、下一秒报
"热降频"。只看最新一次采样,结论几乎永远是"功耗墙",而那 1% 真正热降频的采样
就永远看不见了 —— 偏偏那正是"这张卡 87°C 了要不要管"这个问题要的答案。

实测 Server19(28,240 个样本):

| 掩码 | 原因 | 占比 |
|---|---|---|
| `0x04` | 功耗墙 | 50.5% |
| `0x00` | 无 | 44.6% |
| **`0x20`** | **热降频** | **0.9%** |
| **`0x24`** | **功耗墙+热降频** | 0.03% |

热降频从 **80°C 起出现**,86-87°C 时占该温区采样的 **8.6%**;该机温度目标值是
**85°C**,而 19% 的采样 ≥85°C。所以只报"功耗墙"会掩盖真实存在的散热问题,
现在整机告警会同时给出 `1/8 张卡热降频` 和 `6/8 张卡功耗墙限频`,并在瞬时原因
为"无"时也能报出 `1/8 张卡近期出现热降频`。

> 窗口不足 20 个采样时该列显示 `—` 而不是 `0%`:刚重启时用两个样本得出"0%"，
> 读起来是"这张卡没问题",而实际含义是"还没看够"。

### 显卡利用率趋势

每台机器标题栏右侧有「详情」开关,**默认收起**。展开后立即看到该机器
整机所有显卡的平均利用率趋势,可选 **24 小时 / 3 天 / 7 天 / 30 天**。

图表放在卡片顶部(而不是底部),因为开关的意义就是"看到趋势" —— 放在
八行显卡表和磁盘面板之后,点了详情会像是没反应。

**数据来自 `host_hourly` 表(按小时汇总,永不清理)**,不是原始采样:

| | 明细表(`gpu_sample` / `proc_sample` / `host_sample`) | 汇总表(`host_hourly` / `usage_rollup`) |
|---|---|---|
| 精度 | 每次采集(15 秒) | 每小时 |
| 保留 | `raw_retention_hours`(当前 **720 小时 = 30 天**) | **永久** |
| 体量 | 约 55 万行/天(约 67 MB/天) | 约 144 行/天 |
| 30 天 | 约 **2.0 GB** | 约 4 千行 |

所以 30 天档位不可能用原始数据。汇总表存的是**和与计数**(`util_sum`/`util_n`),
运行平均值在任何采样数下都精确。

- **空闲小时记 0%**,不是空洞 —— `usage_rollup` 只在有人用卡时才有行,
  用它画"这台机器忙不忙"会把闲置时段显示成断线
- **首次升级会自动回填**:表为空时从仍在保留期内的明细表重建,
  否则新功能上线后图表要空等一小时才有数据

### 管理页保存前会检查文件是否被改过

管理页 PUT 的是整份配置。如果页面打开期间文件被别人改了(手工编辑、或另一个管理员保存),
**直接写回就会把对方的改动静默抹掉**。

这不是假设 —— 实际发生过:一个打开的页面手里是 6 台机器的配置,期间文件在磁盘上被改成
15 台,页面一保存,那 9 台就没了。只有 `hosts.json.bak` 恰好留住了它们。

所以加载时服务端给出配置文件内容的指纹(`revision`),保存时前端回传;对不上就返回
**409 并拒绝写入**,提示刷新后重试。宁可让你多点一次,也不能悄悄丢配置。

### 显示顺序 = 配置文件里的顺序

`config/hosts.json` 里 `hosts` 数组的顺序就是看板上机器卡片的顺序。

(曾经不是:State 用 Map 保存主机,而 `Map` 保持**插入顺序**,热重载时新机器被**追加到末尾**。
于是配置里排第一的 gpu03 显示在最后 —— 更糟的是**重启一下顺序又变了**,因为启动时是
按配置顺序建的。现在每次重载都按配置顺序重建,已存在机器的运行状态按引用复用,不受影响。)

### 改配置会自动生效,不用重启

`config/hosts.json` 被监听:保存后约 0.4 秒自动重载,日志里出现
`config reloaded: N hosts, added ..., removed ...`。

**写坏了不会把服务打挂** —— 解析错误记进日志,旧配置继续生效,下次保存再试:

```
config reload FAILED (keeping the previous config): Cannot parse ... (line 82, column 24)
```

(这条设计是因为实际发生过:手工填管理密码哈希时漏了引号,服务进入崩溃重启循环,
日志里只有一行解析错误。)

### 明细保留 30 天的前提:清理必须走索引

保留期从 7 天提到 30 天,明细表会大 40 倍(约 830 万行)。清理每 10 分钟跑一次,
而原本三条 `DELETE ... WHERE ts < ?` 里有**两条是全表扫描** —— 因为
`gpu_sample` / `host_sample` 的索引以 `host_id` 打头,`ts` 范围条件用不上:

```
host_sample   SCAN host_sample            ✗ 全表扫描
gpu_sample    SCAN gpu_sample             ✗ 全表扫描
proc_sample   SEARCH ... USING INDEX (ts<?)  ✓
```

现在三张表都有以 `ts` 打头的索引。顺带删掉了 `gpu_sample` 上两个**已经没有任何
查询会用到**的索引(历史页删除后它们就只剩写入开销:每次采集约 48 行,每行两次
索引更新)。

> `host_sample` 的 `(host_id, ts)` 保留了 —— 启动时"每台机器最新时间戳"那个查询
> 靠它做覆盖索引扫描。

> 这条时间线是"机器忙不忙";"谁用了多少"是另一回事,见「用量」页。

图表的边距是**按标签尺寸量出来的**,不是估的:

| 边距 | 为什么 |
|---|---|
| `left: 0` | 原来是 `-16`,为了省宽度把绘图区左移,结果 Y 轴只剩 30px 给最宽的刻度 —— "100%" 实测 27px,溢出容器左边 5px,**开头的"1"被切掉** |
| `top: 10` | 100% 刻度是**以顶部网格线为中心的**,所以有一半文字在绘图区之上 |
| `right: 30` | recharts 的 x 轴刻度一律**居中对齐**(`text-anchor: middle`),最后一个刻度因此会向右探出半个标签宽度 —— "9/16 12时" 实测 46px,需要 ≥23px |

> 这类问题 jsdom **测不出来**(它不做布局,`getBoundingClientRect()` 全是 0),
> 缩略图上也容易看漏。所以 `npm run screenshot` 现在会检查图表文字是否溢出容器,
> 并输出 `clippedText` 字段;`--expand` 可以先把所有详情展开再截图。
> 实测把边距还原成出问题的值,它会报出 `["9/16 12时", "100%", ...]`。

## 9. 状态灯与失联提示

每台机器左上角是一个**带文字的色块**,不只是一个小圆点:

```
[● 正常] Server19  server19.example.com
[● 连接失败] flaky-node  192.0.2.200
[● 失联] flaky-node  192.0.2.200
```

| 灯色 | 状态 | 触发条件 |
|---|---|---|
| 🟢 绿 `正常` | `ok` | 最近一次采集成功,且数据在 `stale_after_ms` 窗口内 |
| 🟡 黄 `数据陈旧` | `stale` | 超过 `stale_after_ms` 没有成功采集,或采集失败但还没到红灯阈值 |
| 🟡 黄 `连接失败` | `stale` | 同上,但**从未成功采集过** —— 此时没有"陈旧的数据"可言 |
| 🔴 红 `失联` | `down` | 连续失败达到 `down_after_failures` 次 |
| ⚪ 灰 `未知` | `unknown` | 还没尝试过采集(服务刚启动的瞬间) |

两个刻意的设计:

- **灯带文字。** 状态不能只靠颜色表达 —— 色觉障碍、打印、截图都会丢失信息。
  而且原来那个 6px 的纯色圆点**小到容易直接看漏**,而机器状态恰恰是这个看板最重要的信息。
- **「连接失败」和「数据陈旧」是两个词。** 一台从未响应过的机器没有"陈旧的数据",
  说它"陈旧"会暗示我们曾经拿到过读数又丢了。

非健康状态的光点会**呼吸闪烁** —— 闪烁应当只意味着"看这里"。

两个关键设计:

1. **状态由时间戳实时推导,而不是采集时锁存。** 如果轮询进程本身卡死了,不会有任何
   采集结果返回;若把状态锁存,所有机器会永远显示绿色 —— 恰恰漏掉了最该发现的情况。
   服务每秒重算一次状态,并在快照构建时也重算。
2. **失联机器的数据会被明显地"置灰"并标注"数据陈旧 / 机器失联"以及最后成功采集的时间。**
   把过期数据当实时数据展示,是监控看板最危险的失效模式。

状态变化(黄/红/恢复)会写入 `events` 表并在「事件记录」页展示。同一次故障只记一次,
不会每轮重复刷屏。

## 10. 用量统计(年终结算)

### 三套指标,同时累计

`usage_rollup` 表按 **(小时, 机器, 用户)** 永久累计三个积分,因为它们回答的是不同问题:

| 字段 | 含义 | 用途 |
|---|---|---|
| `gpu_seconds` → **占用 GPU 时** | `Σ(占用卡数) × dt` | 公平分配。**占着卡不跑也计费**,实验室通常最关心这个 |
| `sm_gpu_seconds` → **有效 GPU 时** | `Σ(SM利用率)/100 × dt` | 真实算力消耗。跑到 30% 的卡一小时只算 0.3 |
| `mem_mib_seconds` → **显存 GiB·时** | `Σ(占用显存) × dt` | 容量压力,解释"卡看着是空的但我申请不到" |

界面上「用量统计」页把三者并排展示:某用户占 8 张卡跑一天但利用率只有 10%,
会表现为**占用 GPU 时很高、有效 GPU 时很低** —— 这正是年终该讨论的那件事。

### 为什么这样设计能安全清理原始数据

用量是**在写入时就累计**的,不是事后从原始采样重算的。所以:

- 原始表(`gpu_sample` / `proc_sample` / `host_sample`)按 `raw_retention_hours` 定期清理
- `usage_rollup` **永不被清理**

即使原始明细全部删掉,年终报表依然完整。

### 两个刻意的口径选择

- **同一张卡上跑 4 个进程只算 1 张卡**,不会算成 4 张(按 `distinct gpu_index` 计数)
- **多人共享一张卡时,该卡的有效算力按 100% 封顶**,不会因为进程数多而算出超过一张卡的算力

### 停机/重启不会虚增用量

每个样本最多只计入 `2 × interval`。如果服务停了一小时再启动,不会把这一小时当作
"用户一直在满负荷使用"补记进去 —— 少记一点远比凭空多记安全。

## 11. API

| 端点 | 说明 |
|---|---|
| `GET /api/health` | 存活与配置摘要 |
| `GET /api/snapshot` | 当前全量快照(机器 / GPU / 用户) |
| `GET /api/stream` | **SSE** 实时推送快照(前端默认用它) |
| `GET /api/config` | 公开配置(采集间隔、阈值、机器列表) |
| `GET /api/usage/totals?from=-30d&host=` | 按用户汇总用量(年终报表) |
| `GET /api/usage?from=-24h&bucket=3600&user=&host=` | 时间序列用量,`bucket` 秒可重分桶 |
| `GET /api/usage/users` | 近期出现过的用户名 |
| `GET /api/history/machine?host=gpu19&from=-24h` | 该机器按小时的利用率趋势(永不清理的 `host_hourly`) |
| `GET /api/events?limit=100&host=` | 上下线事件记录 |
| `GET /api/admin/session` | 管理页登录状态(无需登录) |
| `POST /api/admin/login` | 登录,成功后下发 HttpOnly 会话 Cookie |
| `POST /api/admin/logout` | 退出登录 |
| `GET /api/admin/config` | 读取可编辑配置(**需登录**) |
| `PUT /api/admin/config` | 保存配置并热重载(**需登录**) |

时间参数支持 epoch 毫秒、ISO 日期(`2026-01-01`)或相对量(`-30m` / `-24h` / `-7d` / `-1y`)。

`/api/snapshot` 的 `summary` 里关于显卡的三个数字:

| 字段 | 含义 |
|---|---|
| `gpus_total` | 总卡数 |
| `gpus_allocated` | 有进程占着的卡 |

空闲卡数 = `gpus_total - gpus_allocated`,**故意不在接口里单独给一份** ——
之前界面顶部同时有「显卡占用」和「空闲显卡」两张卡片,数字互为补数,
等于把同一个数说了两遍。去掉冗余字段能从结构上防止这类重复再长回来。

### 为什么不统计"是否在空转"

曾经有过一个"正在计算 / 空转"的分类(利用率 ≥ 5% 算在算),**已经删掉**,因为它是一个过度断言:

`nvidia-smi` 报的是**瞬时采样值**,而采集间隔是 15s。一个"算几秒、读几秒数据"的训练任务,
完全可能恰好被采到 0%。用一次采样去断定某张卡在空转、某个用户在浪费资源,是不成立的。

而"有进程占着"是**布尔事实**,任何时刻采集都准确 —— 所以只保留这个口径。

**但长时间的平均值依然有效**:同一个不准的瞬时值,一小时采 240 次再平均,就能反映真实消耗。
这正是「用量」页里 `有效 GPU 时` 成立的原因 —— 它是对时间的积分,不是一次快照。
界面上「利用率」列表头也带了提示,说明它只是瞬时值、不能据此判断空转。

实时更新用 **SSE 而不是 WebSocket**:更新是单向的,SSE 自带断线重连、就是普通 HTTP
(nginx / SSH 隧道都不需要额外配置),而且不用引依赖就能实现。

## 12. 数据库

单个 SQLite 文件(默认 `data/gpustatus.db`),WAL 模式,采集写入与 API 读取互不阻塞。

| 表 | 内容 | 生命周期 |
|---|---|---|
| `hosts` | 机器注册表、最近状态、最近错误 | 永久 |
| `host_sample` | CPU / 内存 / 负载 / 磁盘 原始采样 | 按保留期清理 |
| `gpu_sample` | 每张卡的利用率/显存/温度/功耗 原始采样 | 按保留期清理 |
| `proc_sample` | 每进程 用户名/显存/SM 原始采样 | 按保留期清理 |
| `usage_rollup` | 每小时每用户用量积分 | **永久** |
| `events` | 机器上下线、采集异常 | 永久 |

备份只需要拷贝这个文件(`sqlite3 data/gpustatus.db ".backup out.db"`)。

## 13. 部署(systemd)

```bash
sudo cp deploy/gpustatus.service /etc/systemd/system/
sudo vi /etc/systemd/system/gpustatus.service   # 按需修改 User / WorkingDirectory / ExecStart
sudo systemctl daemon-reload
sudo systemctl enable --now gpustatus
sudo systemctl status gpustatus
journalctl -u gpustatus -f                      # 查看采集日志
```

> **注意 `ExecStart` 里的 node 路径。** 单元文件默认写 `/usr/bin/node`(apt 安装的路径)。
> 如果 node 是用 nvm 装的(路径类似 `~/.nvm/versions/node/v24.20.0/bin/node`),
> 必须改成 `command -v node` 的实际输出。systemd 不读 shell 配置,
> 所以这里要写绝对路径,不能依赖 `PATH`。
>
> 可以用这条命令直接生成改好的单元文件:
>
> ```bash
> sed "s#^ExecStart=.*#ExecStart=$(command -v node) server/index.js#" \
>   deploy/gpustatus.service | sudo tee /etc/systemd/system/gpustatus.service >/dev/null
> ```

建议用独立的服务账号(如 `gpustatus`)运行,并把它的 SSH 公钥分发到各 GPU 机器。

## 14. 常见问题

**Q: 界面显示"尚未采集到数据",错误是 `Permission denied (publickey)`**
A: 部署机到目标机的免密 SSH 没配好。用 `ssh -o BatchMode=yes <host> true` 验证。
本服务一律使用 `BatchMode=yes`,不会弹密码提示(否则采集会挂住)。

**Q: 状态灯是黄的,但错误写着 `nvidia-smi failed: Failed to initialize NVML`**
A: 目标机 `nvidia-smi` 本身不可用(驱动/容器/设备问题)。此时探针仍会正常返回,
看板会显示该机 CPU/内存,并标出 `nvidia-smi` 错误 —— 这是刻意设计的,避免整机显示为失联而掩盖真实原因。

**Q: 某台机器 GPU 数是 7 但预期 8**
A: 界面会显示 `显卡 7/8` 告警。通常是某张卡掉出总线或驱动异常,检查 `dmesg` / `nvidia-smi -q`。

**Q: 想加更多机器?**
A: 在 `config/hosts.json` 的 `hosts` 数组里加一项,重启服务即可。目标机器不需要任何改动。

**Q: 采集间隔能改到多快?**
A: 单次采集本身约 0.7~1.0s,所以 5s 也完全可行;但除非确实需要秒级观察,
建议保持 15s 或更慢,以降低对生产机器的干扰。用量统计的精度取决于采样密度,
15s 足以覆盖绝大多数训练/推理任务的时长尺度。

**Q: 前端和后端能分开部署吗?**
A: 能。API 已开启 CORS,`/api/*` 是全部契约;把 `web/dist` 交给任意静态服务器,
把 `vite.config.ts` 里的代理目标改成后端地址即可。默认由后端同源托管,免去 CORS 与跨域配置。

### 为什么需要它

渲染成 HTML(`npm run check:render`)只能证明组件不崩、数据对得上,**看不出页面长什么样**。
下面这些问题前面所有检查都没发现,是**看了截图才发现的**:

| 问题 | 为什么检查发现不了 |
|---|---|
| 「显卡 8/8 占用」画成**满格红条** | 分配率被套用了利用率告警色阶。满卡是正常状态,却让每台机器都像在告警 |
| GPU 利用率 100% 全画成**红色** | 对计算集群来说卡跑满是好消息。满屏红看着像全线故障 |
| 未采集过的机器显示「0 / 0 占用」和「显卡 0/8」红标 | 把"没有数据"当成了"有 0 张卡",凭空断言了未知事实 |

前两个是**语义错误**:红色应该留给需要处理的事(磁盘满、卡过热、机器失联),而不是"资源正在被使用"。

### 环境

需要 `playwright-core`(5MB 驱动,不含浏览器)和一个 Chromium。脚本会自动在
`~/.cache/ms-playwright` 里找已有的 `chrome-headless-shell`;没有的话:

```bash
npx playwright install chromium
```

脚本**故意不用完整的 `chrome` 二进制**:用新版驱动去开缓存里的旧 Chromium,会因
crashpad 参数不匹配报 `chrome_crashpad_handler: --database is required` 而崩溃。
`chrome-headless-shell` 不带 crashpad,跨版本可用。

> 颜色不一致,实际读 `getComputedStyle` 发现五个页签都是同一个 `rgb(22,119,255)`。

## 17. 校验都走 zod

项目里现在**只有一套校验方式**:zod。两处使用:

### 配置文件:`server/config-schema.ts`

`config/hosts.json` 的结构由 schema 定义。相比原来的手写校验(18 处 `fail()`):

- **一次报出全部问题**,而不是遇到第一个就抛。原来改一个配置文件要重启多少次才能改完;
  现在第一次运行就给完整清单
- **每条错误带 JSON 路径** —— `hosts[1].disks[0]: 必须是绝对路径(以 / 开头)`,
  100 行的配置文件不用靠眼睛找
- 消息统一中文(包括 zod 自己的兜底消息)

语义规则(磁盘路径必须是绝对路径、host id 不能重复、`disks` 缺失与 `[]` 是两回事等)用
`.refine()` / `.superRefine()` 表达,行为与原来一致。

> schema 只做**校验**,不做默认值和改名 —— `raw` 保留文档原样,管理页保存时才能
> 原样回写它没有编辑的段落。归一化仍在 `loadConfig` 里。

### 接口:`shared/schema.ts`

## 18. 接口约定(`shared/schema.ts`)

接口的字段定义**只有一处**:`shared/schema.ts` 里的 zod schema。它同时产出三样东西:

1. **前端类型** —— `web/src/types.ts` 现在是 `z.infer` 的转发,不再是 245 行手写 interface
2. **运行时校验** —— 前端每次收到 SSE 推送都过一遍 schema,字段改名或大小写写错会**立刻报错**,
   而不是静默读成 `undefined`
3. **管理页校验** —— 管理页加载配置时同样校验

**为什么值得**:同一个形状原本有**四份手工维护的副本**,而且已经漂移过:

| 副本 | 问题 |
|---|---|
| `web/src/types.ts` | 245 行 interface |
| `render-check.tsx` 的 `CONTRACT` 表 | ~60 个字段名,**`note` 写了两遍** |
| `server/state.js` | 实际发出的东西 |
| `AdminView.tsx` 本地 interface | 第四份 |

真实事故就是这么来的:服务端发 `totalMib` 而类型声明 `total_mib`,磁盘数字渲染成 `— / —`,
没有任何报错。另一次是 `net_mounts` 漏出管理接口,管理页直接白屏。

> Node 24 可以直接 import `.ts`(类型擦除),所以前后端**共用同一个文件**,不需要构建步骤。

## 19. 测试

```bash
npm test                          # 全部单元测试(后端 + 前端主题不变量)
npm run typecheck                 # 前端 TypeScript 类型检查
npm run check:render              # ★ 渲染冒烟测试(需要后端正在运行)
```

`check:render` 会**从正在运行的后端拉取真实快照**,把 `Overview` / `UsersView`
(即 `Machine` 整棵数据渲染树)渲染进 **jsdom**,然后对真实 DOM 做断言:

- 每台机器一张卡片,每张卡一行(按机器数、卡数核对)
- 序号单元格 / 型号单元格 / 磁盘方块 / 网络挂载块 / 用户行的**数量**
- 每个用户名、型号名都出现在**可见文本**里
- 可展开行、降频标记、边界场景(idle 卡、一卡三人、进程属主丢失)
- 输出中不含 `undefined` / `NaN` / `[object Object]`
- 两套主题算法产出的 `--ant-color-bg-container` 不同,且暗色确实更暗

类型检查和接口字段比对只能证明"结构对得上",只有真正渲染一遍才能证明组件
**遇到真实数据不会崩**。

> **这里原本是渲染成 HTML 字符串再用 `countOf('gpu-row')` 数字符串出现次数。**
> 那个做法错得很实在:给行再加一个 `gpu-row-expandable` 类之后,每行被数成两次
> (48 行报成 95 行);类名叫 `cell-model-REMOVED` 也照样能匹配上 `cell-model`。
> 两次都真的发生过。换成元素查询后,这两个失败模式从根上不存在。

`npm test` 里前端那部分只留**比对两件必须一致的产物**的测试:
`index.html` 的预绘制脚本和 `theme.ts` 的 `localStorage` key 是否一致
(不一致的表现是"用户保存的主题选择被忽略",不报错),以及颜色是否都来自
antd token。

> 这里删掉过三个测试,它们断言的是**源码里存在某段文字**——`App.tsx` 里有
> `darkAlgorithm`、`severity.ts` 里有 `colorSuccess`、`Machine.tsx` 里有
> `host.group !== site`。这种测试会因为**重构**而失败,不会因为**行为坏了**而失败。
> 同样的保证现在由渲染检查真实渲染两套主题来提供。
